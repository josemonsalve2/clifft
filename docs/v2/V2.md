## 0. TL;DR recommendation

Build V2 as **one operand library authored in a non-HIP device language,
driven by a persistent runtime interpreter kernel, dispatched via HSA, with
per-circuit specialization applied by progressive lowering — not by unrolling
the operand sequence.** Delete the hand-emitted MLIR text emitter. Keep the
HSA runtime, the bytecode ISA, and the SVM/CPU operand *math* as the
correctness reference. Make rank and qubit caps config-driven from day one.

The single most important reframing: **the V1 failure was UNROLLING THE
OPERAND SEQUENCE, not compiling per circuit, and not "runtime vs compiled."**
The real design axis is *specialization granularity*: specialize the operand
*body* (constants, rank, matrices) while keeping loops over shots, over the
bytecode, and over amplitudes.

The single most important CONSTRAINT (R6): **no HIP.** This removes "double
down on Hybrid" and "templated `__device__` HIP library" from the table and
forces the device source of truth to be LLVM-IR / MLIR / plain-C→amdgcn — all
of which the existing HSA back-half of the pipeline already loads.

## 1. What each existing path earns (R0)

| Path | What it is | Earns its keep? |
|------|-----------|-----------------|
| **CPU SVM** (`sample_survivors`, f64) | scalar interpreter | YES — the physically-true correctness oracle. Keep as gold #1. |
| **GPU SVM** (`hip_sampler.hip:729`, f32) | runtime bytecode interpreter kernel, **written in HIP** | Conceptually the model V2 wants (loop, not unroll). But it is a HIP kernel (R6 forbids shipping it) and it is the thing a "V2 interpreter" risks merely rebuilding (R0). Keep as gold #2 *reference*; its device form is not the V2 device path. |
| **Hybrid** (`codegen/`, HIP compiled per circuit) | per-circuit HIP kernel, compact-ish loop | Fast + correct, but **HIP** (R6 forbids). Its *operand math* and its post-clang LLVM-IR are salvage; the path itself cannot be V2. |
| **MLIR** (`mlir_emit.cc`, 3424 lines) | hand-emitted, fully-unrolled IR text | The MLIR BACKEND stays (V2 rebuilds it). What is retired is the current EMITTER — unrolling is its architecture, nothing to salvage in its 3424 lines. Its HSA compile+dispatch *back-half* (`-x ir`→llc→lld→hsaco→HSA) is exactly the HSA-only device path V2 needs — **keep the pipeline, replace the front-end emitter.** |

**Conclusion (R0):** the "device-agnostic, faster-than-both, HSA-only" slot MLIR
was meant to fill is REAL and still open — but only because of R6. Without the
no-HIP rule, the right answer would be "keep SVM+Hybrid, delete MLIR." With
R6, we need a non-HIP device path, so V2 must build one — and it should be the
*single* device path, not a fourth parallel one.

## 2. Root cause of V1 (from reference_v1.md, verified)

1. **Triple–to–septuple duplication.** Each opcode is hand-written in CPU-SVM,
   GPU-SVM, Hybrid register + Hybrid coop templates, and MLIR — and coop/global
   get their own variants. ~40 opcodes × 5–7 sites. Drift bugs are structural
   (the MULTI_CNOT px/pz-swap that only existed in MLIR;
   `mlir_array_ops.inc:426`, fixed this session).
2. **Full unrolling of the operand sequence (MLIR).** Three `for(pc) switch(op)`
   emit-loops append inline IR per instruction (`mlir_emit.cc:2377,2867,3297`).
   16432-op circuit → 20 MB IR → won't link; 115 KB/thread spills; 55–224 s
   compiles; 5–60× slower at runtime.
3. **Correctness fragility with no shared code.** Divergent barriers hang
   AMDGPU; coop RNG threading (tid0-only vs redundant-full); f32/f64
   accumulation; struct byte-layout; HBM stride. Each rediscovered per backend.

Note (from the IR oracle): even **Hybrid** HIP is large for U2/U4-heavy
circuits (coop_qv10 33.5k lines HIP; surface_d7_t10 75k lines / 398k O0.ll).
Hybrid emits per-instruction code too — just more compactly and via a real
compiler. **A V2 that keeps the operand sequence a true runtime loop can be
smaller than Hybrid, not merely equal.**

## 3. The V2 architecture

### 3.1 What must stay a loop vs what may be specialized (precise)

The V1 disease was unrolling the **operand SEQUENCE** (one inlined IR block per
bytecode instruction). It is NOT "never unroll anything." Be precise about the
three loops — they have DIFFERENT rules:

- **Loop over shots — ALWAYS a runtime loop.** Persistent kernel, grid-stride /
  work-stealing pull (IRIS mega-kernel pattern). Never unrolled; shots are data.
- **Loop over the bytecode — ALWAYS a runtime loop (this is the whole point).**
  `for (pc) ... dispatch(bytecode[pc])`. The operand SEQUENCE is data walked at
  runtime, never emitted per-instruction. This is what kills the 20MB-IR /
  spill / slow-compile disease. GPU-SVM already has this shape
  (`hip_sampler.hip:729`).
- **Loop over amplitude GROUPS — STAYS A LOOP for nontrivial rank.** The sweep
  over `2^(k-2)` (U4) / `2^(k-1)` (U2) amplitude groups is NOT fully unrolled —
  at rank 10 that is 256–512 groups; flattening it would reintroduce the bloat.
  What MAY specialize: rank/axis/stride/matrix values become immediates,
  enabling vectorization and *bounded partial* unrolling. **Only the fixed
  2×2/4×4 complex butterfly arithmetic inside the loop body is fully unrolled**
  (it is a constant 4–16 multiply-adds). Tile-structured (see §3.3).

**Precise rule (per CODEX_REVIEW.md §3, authoritative):** shot loop + bytecode
loop = ALWAYS runtime loops (never unrolled — this was the disease). Amplitude-
group loop = a loop too, but its bounds/constants may specialize and it may be
vectorized / bounded-partial-unrolled. The 2×2/4×4 butterfly = fully unrolled.
See §3.2bis for how per-circuit constants reach shared operand code (Mode I vs
Mode S) — noting Codex flags Mode S's mechanism as still unspecified; that must
be resolved (CODEX_REVIEW.md §8 item 2) before Mode S is built.

### 3.2 Single operand source of truth — but NOT in HIP (R6)

pre_V2 proposed one templated `__device__` HIP library. R6 forbids HIP. The
operand math is plain arithmetic + memory, so re-home it. Candidate authoring
languages for the ONE operand library, ranked by pragmatism:

1. **Plain C / OpenCL-C → amdgcn-amd-amdhsa via clang device-libs (no `-x hip`,
   no HIP runtime).** ✅ **PROVEN buildable on this toolchain** — see
   `experiments/exp1`: `clang --target=amdgcn-amd-amdhsa -mcpu=gfx950
   -ffreestanding -nostdlib -emit-llvm` → `llc` → `ld.lld -shared` produces a
   valid AMD-GPU ELF `.hsaco` with the kernel FUNC + `.kd` descriptor HSA needs,
   using `__builtin_amdgcn_workitem_id_x` etc. (no HIP runtime). This removes the
   biggest toolchain-reality risk in the whole plan. One `.bc`/`.ll` per operand,
   linked into the interpreter
   kernel, HSA-loaded. Keeps C-level single-source authoring, satisfies HSA-only,
   lets clang specialize. **Lowest infra; try first.**
2. **MLIR custom `quantum` dialect + progressive lowering passes → LLVM-IR →
   llc/lld → HSA.** One operand = one dialect op with a lowering rule. This is
   where MLIR-the-FRAMEWORK (not hand-emitted text) earns its keep and where R5
   (progressive-lowering specialization) lives. **Most infra; most device-
   agnostic + best specialization control.**
3. **LLVM-IR operand-function library (llvm.func per operand), interpreter loop
   calls them.** The `@clifft_log`/`@clifft_draw_next_noise` shared-function work
   done this session is a proof of concept. Hand-authored IR is brittle; prefer
   #1 or #2 to generate it.

The **SVM/Hybrid operand bodies are the semantic reference** for whichever
language wins — a re-homing of battle-tested logic, not a re-derivation.

### 3.2bis The specialization⇄shared-body tension (Codex review — must resolve)

There is a real tension the earlier drafts glossed: a **single shared operand
function** walked by a runtime loop means the operand reads its arguments
(axis, matrix, rank) as **runtime values from the bytecode/ConstantPool** — so
it is NOT specialized. But R5 wants per-circuit **body** specialization (burn
matrices/rank into immediates). You cannot have one un-cloned shared body AND
per-body constant-folding at the same time for the same instance. Resolve by
being explicit that these are **two distinct operating modes on ONE source**:

- **Mode I — Interpreter (default, always correct, zero per-circuit compile):**
  the shared operand functions take runtime args. One kernel per tier, walks any
  circuit's bytecode. No specialization; constants are loads. This is the
  baseline V2 ships and the thing SVM proves is correct.
- **Mode S — Specialized (opt-in, per-circuit, JIT):** the SAME operand source
  is instantiated with circuit constants as template/compile-time parameters
  (rank, U2/U4 matrices, axis indices), producing a specialized-but-still-
  LOOPED kernel (loops over shots + bytecode preserved; inner sweep specialized).
  This is a per-circuit compile, gated on being worth it.

Crucially, **Mode S does NOT unroll the operand sequence** — it specializes each
operand's body while the bytecode loop remains. The single source of truth is
preserved because both modes `#include`/instantiate the same operand
definitions; Mode S just binds some args at compile time. The px/pz-swap bug
class stays impossible (one definition).

**This makes the P2 decision-gate (§6) the pivot of the whole design:** measure
Mode I (interpreter) vs Hybrid. If Mode I reaches parity, we may never need Mode
S (or the dialect). If it doesn't, Mode S / the tile dialect is where the
specialization lives. Do not build Mode S or the dialect before that number.

### 3.3 The TILE / fine-grained-task model — the core V2 pillar (R7)

GPUs are no longer flat SPMD. The through-line from ThunderKittens/HipKittens,
Composable Kernels, and cuTile is a **programming model**, not a library
(their code is HIP/CUDA C++ — R6 forbids vendoring): **tiles are the unit of
data**, a workgroup/wave owns a tile and cooperates on it, and work splits into
**fine-grained tasks with an explicit memory↔compute split** (producer waves
move data, consumer waves compute, overlapped by async pipelines).

This maps onto quantum simulation almost exactly:
- **The amplitude sweep IS a tile op.** A U4 gate = read 4 amplitude planes →
  4×4 mul → write 4 planes, over a tile of `2^(k-2)` groups. V1 does this as a
  flat strided SPMD loop with hand-rolled `ds_bpermute`. A tile op expresses it
  natively.
- **The memory/compute split is per-operand-class real:** measurement =
  bandwidth-bound reduction; gate = compute-bound butterfly; noise/frame = tiny
  scalar bookkeeping. A producer/consumer schedule can overlap the measurement
  reduction of stage N with the gate math of stage N+1 — exactly what V1's
  bulk-synchronous barriers forbid.
- **The coop tier is a tile-cooperation problem:** 256 threads on one
  LDS statevector = "a workgroup owns a tile." Getting this wrong is where V1
  hit divergent-barrier hangs.

**This is the strongest argument for MLIR-the-framework (device option #2) over
plain-C (#1):** MLIR can carry the tile abstraction as a first-class dialect op
(`quantum.gate_sweep` over a statevector tile) and make the memory/compute
split + async pipelining a **lowering/scheduling pass**, instead of
hand-written barriers. Plain-C would hand-roll the schedule again.

**Two hard corrections from the tile-model research
(`tile_model_for_mlir_v2.md`), both devil's-advocate wins:**
1. **Matrix cores (MFMA) are a TRAP for us.** Every tile library
   (ThunderKittens/HipKittens/CK/cuTile) exists to feed matrix cores with large
   GEMMs. Our gate "compute" is a 2×2/4×4 complex butterfly (K=4 vs MFMA's
   native K≥8), and batching butterflies into a structured matmul costs more in
   pack/transpose/complex-expansion than it saves. **Keep MMA out of the
   dialect.** What transfers from these projects is ONLY the tile
   data-movement/cooperation/reduction model, not their compute primitives.
2. **The async producer/consumer pipeline is probably UNNECESSARY for the
   shot-parallel tiers.** Its whole purpose is to hide memory latency behind
   compute — but with ~10000 embarrassingly-parallel shots, GPU *occupancy*
   already hides that latency (many resident workgroups). HipKittens itself
   reports wave-specialization / ping-pong *underperforms* on CDNA3/4. So R7's
   "memory↔compute split via async pipeline" likely applies, if anywhere, only
   to the single-shot coop/global cooperation — NOT as a cross-shot schedule.
   **Adopt the tile abstraction for cooperation + measurement reduction;
   treat the async pipeline as measure-first, likely-cut.**

Net: the tile model's value for V2 is concentrated in (a) expressing the
cooperative amplitude sweep + measurement reduction as clean tile ops (fixing
the hand-rolled ds_bpermute bug class), and (b) register-pinning/layout to kill
the 115 KB coop/global spills — NOT in matrix cores or cross-shot pipelining.

### 3.4bis Specialization by progressive lowering, not unrolling (R5)

Specialize the operand BODY per circuit; keep the SEQUENCE a loop:
- Burn ConstantPool U2/U4 matrix values, axis indices, and the **exact rank**
  (fixes inner-sweep trip count → compiler unrolls/vectorizes the tile
  butterfly) into immediates.
- Keep the outer bytecode loop and shot loop intact; specialize *within* the
  tile op.
- Each **tier is a lowering target** (register/coop/global tile backing), not a
  hand-written kernel.

**Devil's advocate (unresolved, needs measurement):** does the tile-dialect +
progressive-lowering path beat "plain-C operand lib + clang specializes a
per-circuit runtime loop" by enough to justify a dialect + passes? HipKittens
found fancy schedules often underperform simple ones on CDNA3/4, and the
interpreter tax over Hybrid is real (SVM ~1.3× slower than Hybrid). **Prototype
the highest-value specialization (fixed-rank tile-sweep + constant U2/U4
matrices, with a producer/consumer measurement/gate overlap) and measure before
committing to the dialect (P2 gate, §6).**

### 3.4 Tiers — unify the source, minimize compiled specializations (R1)

The 3 tiers differ only in statevector storage (private / LDS addrspace-3 / HBM)
and cooperation (1 vs 256 threads/shot). Operand math is identical.
- **Unify the SOURCE**: one operand library, tier as a compile-time parameter
  (storage address space + cooperation predicate). HK tile container abstraction
  (register-tile / shared-tile / HBM-streamed-tile) is the clean model —
  *reimplemented* in the non-HIP language (HK itself is a HIP header lib, R6).
- **Minimize compiled kernels**: likely 2–3 specializations, not 3 hand-written
  kernels. Open hypothesis to TEST: can register fold into coop with an adaptive
  workgroup size + shot-packing (§3.5), collapsing to **coop + global** only?
- Barriers live INSIDE coop operand functions; the bytecode loop is uniform
  across threads → divergent-barrier hangs become structurally impossible
  (enforce: no data-dependent skip of an operand across cooperating threads).
  Use IRIS SC-HRF scoped fences (`workgroup`/`agent`).

### 3.5 Shot parallelism (owner's earlier question, folded in)
- **Shot-packing at low coop rank** is the one clear lever: rank-5 coop runs 256
  threads over 32 amplitudes (~87% idle). Pack multiple shots/workgroup at low
  rank. This is also the mechanism that could merge register into coop (§3.4).
- **Shared deterministic prefix**: measure-first, likely small (surface codes
  branch early); forking the statevector costs bandwidth.
- **Cross-shot pipelining**: the hardware already does this via occupancy; not
  worth explicit software effort.

### 3.6 Design out artificial limits (R4)
- `kGlobalMaxPeakRank=19` is ARTIFICIAL (a constant). Make global storage
  **rank-parametric**: slot size = `sizeof(complex)<<rank`, capped only by HBM
  (rank 20 = 8 MB/slot × 512 slots = 4 GB; fine on 288 GB). Unblocks qv20.
- `kPauliWords` config-driven (done this session, =5). Keep it a config.
- FUNDAMENTAL limits: HBM size (max rank), LDS 64 KB (coop rank ≲10 →
  above that, global). Everything else is a constant to delete.

## 4. Correctness strategy (R2, R3)

1. **Correctness before performance.** All 22 BENCHMARKS.md + test circuits must
   match gold at **O0 first** (bugs reproduce at O0 — verified this session), then
   climb O0→O1→O2→O3, re-verifying at each rung and recording the perf delta.
   Keep a `CLIFFT_OPT` knob.
2. **Two golds (R3).** CPU-SVM (f64) = physically-true oracle; GPU-SVM (f32) =
   the model V2's f32 device path must match bit-for-bit (same RNG + f32 → exact
   `passed_shots`). CPU may differ by a few borderline-branch shots — that
   tolerance is expected and must be encoded in the test harness.
3. **Per-operand unit IR + differential tests.** One implementation → a failing
   per-operand test localizes to one function. Use the `ir_reference/` oracle
   (now includes MLIR .ll AND Hybrid post-clang .ll at O0/O2) as a codegen
   regression net.
4. **Barrier/divergence lint** on the interpreter loop (uniform operand sequence
   across cooperating threads).

## 5. What to keep vs rebuild (migration)

**KEEP (correct, orthogonal to the codegen problem):**
- HSA runtime + PersistentDispatcher (`gpu/runtime/hsa_*`) — already HIP-free.
- The `-x ir`→llc→lld→.hsaco→HSA compile+dispatch back-half of the MLIR
  pipeline — this IS the HSA-only device path R6 wants.
- Bytecode ISA + ConstantPool (`backend.h`), back-end lowerer, StatevectorSqueeze.
- SVM/CPU operand math as the semantic reference.
- The `ir_reference/` corpus (MLIR + Hybrid oracle) as verification.

**REBUILD:**
- The device operand path: one non-HIP operand library + runtime interpreter
  kernel + (optional) progressive-lowering specialization.

**DELETE:**
- `mlir_emit.cc`'s hand-written unrolling emitter (3424 lines).
- The Hybrid HIP path AS A SHIPPED BACKEND (R6) — but mine its operand bodies
  and keep it as an offline oracle generator.

## 6. Reimplement vs re-adapt — the call

**Reimplement the device operand path; re-adapt everything around it.** The
codegen core (unrolling) has nothing to salvage; the infra (HSA dispatch,
ISA, pipeline back-half, operand math) is correct and reused. This is a
targeted rewrite of one subsystem, not a from-scratch project.

**Decision gate before committing the dialect (R5/§3.3):** build the smallest
persistent interpreter kernel for ONE tier in the plain-C→amdgcn path (option
#1), HSA-dispatched, and benchmark vs GPU-SVM and vs Hybrid on qv10 +
circuit_d5 + surface_d7. If plain-C interpreter reaches Hybrid parity, the MLIR
dialect (option #2) is optional polish. If it doesn't (register-tier dispatch
overhead, or missing specialization), invest in progressive lowering. **Do not
build the dialect before this measurement.**

## 7. Phasing (revised per CODEX_REVIEW.md §16 — authoritative)

- **P0 — De-risk & freeze (no device operand code yet).**
  (a) **CMake decoupling — MLIR-V2 SIDE ONLY (owner constraint: do NOT touch how
      SVM/Hybrid build).** Do NOT restructure the existing `if(CLIFFT_ENABLE_HIP)`
      block — it stays byte-for-byte (keeps `enable_language(HIP)`, `hip::host`,
      `hip_sampler.hip`, the Hybrid codegen). Instead add a SEPARATE, independent
      `CLIFFT_ENABLE_MLIR_V2` configuration + `run_v2` target that REFERENCES the
      already-HIP-free files (`gpu/device_program.cc`, `gpu/runtime/hsa_runtime.cc`,
      `hsa_kernel_dispatch.cc`, `hsa_persistent_dispatch.cc` — verified: their only
      "HIP" mentions are comments, no HIP include/API) and links ONLY
      `hsa-runtime64` (no `enable_language(HIP)`, no `hip::host`). The same `.cc`
      can be listed in two independent build configs; used in separate build dirs
      (`build-v2-nohip` vs the existing HIP build) they never interfere. This
      satisfies R6 for V2 WITHOUT any change to the SVM/Hybrid build path.
      Add a CI check that the `run_v2` binary links no HIP runtime. (Supersedes
      CODEX_REVIEW.md §7/§16's "move sources out of the HIP branch" — that would
      touch SVM/Hybrid; the reference-from-separate-config approach does not.)
  (b) **Checked-in compile/load probe** (`cmake/ClifftAmdgcn.cmake`): pin
      clang/llc/ld.lld from `LLVM_PREFIX`; `--target=amdgcn-amd-amdhsa
      -mcpu=gfx950 -nogpulib`; fail on any `-x hip`. (Toolchain already proven:
      `experiments/exp1,exp2`.)
  (c) **Freeze the device ABI**: the V2 wire format is `GpuInstr` + flattened
      pools (`gpu/device_program.cc:57-114`), NOT the 32-byte VM `Instruction`.
      Version it; add C/C++ `static_assert` offset/size tests.
  (d) **Freeze the numeric contract** (not just "f32/f64"): amplitude/matrix/
      gamma/reduction precision, FP-contraction, denormals, fast-math,
      transcendental impl, reduction order, RNG consumption, Mode I≡Mode S,
      CPU-tolerance vs GPU-exactness. Reconcile GPU-SVM `-ffp-contract=off`
      (`CMakeLists.txt:106-109`) vs Hybrid `-ffast-math` before calling GPU-SVM
      bit-exact gold.
  (e) Differential harness vs CPU + GPU-SVM.
- **P1 — THE FIRST SLICE (CODEX_REVIEW.md §7).** A fixed-rank-10 coop
  interpreter for the **qv10 opcode subset** (FRAME_H, FRAME_S, ARRAY_ROT,
  ARRAY_U2, ARRAY_U4, EXPAND_ROT, MEAS_ACTIVE_INTERFERE, SWAP_MEAS_INTERFERE +
  test-only OBSERVABLE), plain C, no device libs, HSA-loaded, with TWO entry
  points in one source: `clifft_v2_coop_direct` (one block/shot) and
  `clifft_v2_coop_persistent` (atomic-pull). Exact xoshiro RNG, f32 amp / f64
  reduce, workgroup-scope barriers, existing scatter-LUT strategy. Files +
  build commands + **predeclared prove/kill criteria** are in CODEX_REVIEW.md §7.
  Do NOT extract all operands, do other tiers, build Mode S, or start a dialect.
- **P2a — Architecture/workload gate (replaces the old single P2).** Compare
  GPU-SVM / plain-C direct / plain-C persistent / exact-rank-AOT / Hybrid / a
  thin direct-call MLIR control across register+coop+global reps. Measure cold
  compile, load, warm kernel, whole-call latency, shots×distinct-circuit
  workload matrix, IR/code size, VGPR/SGPR/private/LDS, branch/SALU/i-cache
  proxies, correctness. Predeclared thresholds (CODEX_REVIEW.md §7 kill-list:
  e.g. kill plain-C if direct >1.35× GPU-SVM kernel time after matching
  scheduling; do NOT kill merely for 20-35% behind Hybrid).
- **P2b — Specialization gate.** One narrow specialization in plain-C/LLVM vs
  minimal MLIR lowering. Only if this + a custom-dialect RFC (ops/types/
  TableGen/lowering/tests/maintainers/size/fallback) justify it does the dialect
  begin.
- **P3** All opcodes + remaining tiers (register-merge-into-coop experiment;
  global with work-stealing + rank-parametric storage). All 22 circuits at O0.
- **P4** Climb O0→O3, measure each rung. Shot-packing at low rank.
- **P5** Remove `mlir_emit.cc` and the shipped Hybrid backend ONLY after the
  replacement passes all correctness + no-HIP-linkage + performance gates.

Each phase is independently shippable and ends at a commit.

## 8. Open questions for the ultrathink phase

1. Plain-C→amdgcn (no HIP) toolchain details: which clang flags/device-libs
   produce an HSA-loadable `.hsaco` without the HIP runtime? (The MLIR path's
   `-x ir` + `--offload-arch` + llc/lld is the proven template.)
2. Does a runtime `switch(opcode)` cause warp divergence / i-cache pressure that
   negates the compactness win? (Interpreter dispatch cost — measure at P2.)
3. Can register tier merge into coop via shot-packing without occupancy loss?
4. Progressive-lowering specialization ROI vs clang-per-circuit (§3.3 gate).
5. Numeric model: exactly where f64 is load-bearing (gamma, probability sums,
   deep-trajectory renorm) vs f32 amplitudes.
6. Precompiled tier kernels (zero per-circuit compile) vs per-circuit JIT for
   specialization — amortizing the ~200 ms HSA loader cost.
7. Can multi-qubit gate butterflies be reformulated as small GEMMs to use MFMA
   (HipKittens open question), or is a custom bulk operator the right call?
   (Default: custom bulk operator; MFMA is a stretch.)
8. Forced-measurement (`OP_*_FORCED`) bytecode-rewrite path must flow through
   the interpreter unchanged.

## 9. One-paragraph recommendation

Retire the unrolling MLIR emitter and the HIP backends as *shipped paths*. Keep
the HSA runtime, the ISA, the pipeline back-half, and SVM/CPU as gold. Build ONE
operand library in a non-HIP device language (start plain-C→amdgcn), drive it
with a persistent runtime interpreter kernel (IRIS mega-kernel pattern) whose
three loops — shots, bytecode, amplitudes — are never unrolled, with tiers
unified in source (HK tile pattern, reimplemented) and specialized per circuit
by the compiler and, if measurement justifies it, a progressive-lowering
`quantum` MLIR dialect. Bring all 22 circuits to correctness at O0 against both
golds first, then climb O0→O3. Make rank/qubit caps config, not constants.
Gate the dialect investment on a P2 interpreter-vs-Hybrid benchmark.
