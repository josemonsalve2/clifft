# 1. Executive verdict

**V2.md is not ready to implement as an architecture.** Its diagnosis of V1 is strong and verified: the hand emitter expands the bytecode sequence three times into per-instruction IR (`src/clifft/gpu/mlir/mlir_emit.cc:2377-2414`, `src/clifft/gpu/mlir/mlir_emit.cc:2867-2903`, `src/clifft/gpu/mlir/mlir_emit.cc:3297-3333`), and the measured IR size, 115,224-byte private segment, compile-time blowups, noncompiling large circuits, and 5-60x runtime losses are real (`results/d11err_49530.log:16-22`, `results/gt19_49517.log:5-12`, `results/perf2_49532.log:5-15`). Replacing that emitter and preserving the HSA loader/back-half is the correct direction.

The decision document nevertheless has five implementation-blocking holes:

1. **It still does not guarantee that MLIR survives.** The clarified wording says “rebuild MLIR,” but the recommended plain-C Mode I can ship without Mode S or a custom dialect (`V2.md` sections 3.2, 3.2bis, and 6). That is a plain-C/HSA backend using old infrastructure, not an MLIR-backend rebuild.
2. **Mode S is not implementable as described.** A dynamic `pc` loop cannot make per-instruction axes and matrices compile-time constants without a per-`pc` dispatch, function clones, or a specialization-ID representation. “Two modes on one source” names the conflict but does not solve it.
3. **The no-HIP path is not an end-to-end build today.** The reusable LLVM/HSA back-half is real (`src/clifft/gpu/mlir/mlir_kernel_cache.cc:144-175`, `src/clifft/gpu/runtime/hsa_kernel_dispatch.cc:117-179`), but HSA/MLIR are currently compiled only under the HIP build branch (`src/clifft/CMakeLists.txt:86-124`). The available LLVM 21 toolchain supports gfx950 but lacks discoverable ROCm device libraries; a plain-C loadable-kernel probe has not been demonstrated.
4. **The P2 gate cannot answer the decision it claims to answer.** It changes compiler frontend, scheduling, interpreter structure, and operand code simultaneously; covers essentially one tier; ignores circuit-variety amortization; has no predeclared thresholds; and tries to decide dialect ROI without a dialect comparator.
5. **The ABI, numeric model, and tier abstraction are not frozen.** The device uses flattened `GpuInstr`, not the 32-byte VM union (`src/clifft/gpu/device_program.cc:57-114`); f32/f64 and FP flags differ across references; and private/LDS/HBM tiers require distinct typed address spaces and execution adapters.

The three just-applied fixes are therefore **(a) partial, (b) inadequate, and (c) partial**. Scope wording is cleaner but contradicted by the plain-C/no-dialect winning branch; Mode S lacks a mechanism; and the loop distinction is re-broken in sections 0 and 9 and still risks implying full unrolling of a large amplitude-group sweep.

**What must change first:** apply section 8 items 1-9 to `V2.md`, then implement only the section 7 first slice: a no-HIP, fixed-rank-10 coop interpreter for the qv10 opcode subset with direct and persistent scheduling variants. That slice should prove or kill the toolchain, device ABI, switch, cooperative barrier/reduction, and scheduling bets. Do not begin all-opcode extraction, tier unification, Mode S, or a custom dialect until that evidence exists.

# 2. R0-R7 compliance

- **R0 — SATISFIED.** `V2.md` section 1 explicitly acknowledges that GPU SVM is already the runtime interpreter, keeps SVM/Hybrid as references, and gives the new path a distinct reason to exist: a non-HIP, HSA-dispatched MLIR backend (`V2.md` section 1, especially the table and conclusion; section 6's P2 gate). This is adequate framing even though the performance justification remains conditional.
- **R1 — PARTIAL.** `V2.md` section 3.4 says “unify the source” and proposes testing whether register can fold into coop, but it neither quantifies the occupancy/divergence cost requested by R1 nor defines a credible common ABI across private, LDS, and HBM storage. The current implementations are materially different, not merely one pointer parameter: register uses an inline private `ShotState::v` (`src/clifft/gpu/sampler/hip_sampler.hip:145-155`), coop uses an explicit pointer-rich `CoopShotState` plus barriers and LUT state (`src/clifft/gpu/sampler/hip_sampler.hip:864-883`), and global adds HBM slots and work stealing (`src/clifft/gpu/sampler/hip_sampler.hip:1937-1979`).
- **R2 — SATISFIED.** `V2.md` section 4 item 1 and section 7 P0-P4 require correctness at O0 before performance, then O0->O3 verification with an optimization knob. That directly answers R2.
- **R3 — PARTIAL.** `V2.md` section 4 item 2 names CPU f64 and GPU SVM f32 as the two golds and states the intended tolerance model, but “same RNG + f32 -> exact passed_shots” is not a sufficient numeric contract. GPU SVM is compiled with FP contraction disabled (`src/clifft/CMakeLists.txt:106-109`), while Hybrid JIT uses `-ffast-math` (`src/clifft/gpu/codegen/kernel_cache.cc:107-118`); the design does not freeze contraction, denormal, reduction-order, or transcendental semantics for Mode I.
- **R4 — PARTIAL.** `V2.md` section 3.6 states the right intent for rank-parametric storage and configurable frame width, but it overstates the current state and does not define an ABI-safe mechanism. `kPauliWords` is still a compile-time constant (`src/clifft/gpu/gpu_types.h:25-31`), while the current Hybrid source generator still hardcodes two words in register, coop, global, Pauli application, and emitted constant data (`src/clifft/gpu/codegen/emit_preamble.cc:90-101`, `src/clifft/gpu/codegen/emit_coop_kernel.cc:85-97`, `src/clifft/gpu/codegen/emit_global_kernel.cc:90-99`, `src/clifft/gpu/codegen/ops/frame_ops.inc:25-29`, `src/clifft/gpu/codegen/emit_preamble.cc:402-417`). The rank-20 memory example also counts the 8 MB statevector but omits per-slot scratch and other allocations; current global code allocates scratch at half the statevector size (`src/clifft/gpu/sampler/hip_sampler.hip:1941-1944`, `src/clifft/gpu/sampler/hip_sampler.hip:2159-2170`).
- **R5 — GAP.** `V2.md` section 3.2bis asserts Mode S can bind per-instruction axis/matrix constants while retaining a runtime `pc` loop, but provides no representation that makes a dynamic bytecode record a compile-time value. Section 3.4bis promises body specialization, while section 6 gates only an unspecialized interpreter; it does not perform R5's required fixed-rank/constant-U2/U4 comparison “both ways” before committing to the dialect. This is a blocking architectural hole, not missing implementation detail.
- **R6 — PARTIAL.** The proposed device source and dispatch path obey the no-HIP rule in principle (`V2.md` sections 0, 3.2, and 5), and the LLVM-IR back-half really does use `llc`/`ld.lld` and HSA loading (`src/clifft/gpu/mlir/mlir_kernel_cache.cc:144-175`, `src/clifft/gpu/runtime/hsa_kernel_dispatch.cc:117-179`). However, the repository currently compiles the HSA runtime and MLIR backend only inside `if(CLIFFT_ENABLE_HIP)`, enables the HIP language, and links `hip::host` (`src/clifft/CMakeLists.txt:86-124`); even `run_gpu` is created only when HIP is enabled (`CMakeLists.txt:187-194`). `V2.md` does not acknowledge or plan this required build-system decoupling.
- **R7 — PARTIAL.** `V2.md` section 3.3 correctly rejects MFMA for 2x2/4x4 butterflies and treats CDNA producer/consumer scheduling skeptically, but then makes the custom tile dialect optional behind P2. Mode I can therefore become the shipped V2 without any tile IR or explicit memory/compute model, contrary to R7. The document must state which non-optional tile/cooperation abstraction survives if the dialect is rejected.

# 3. Correctness of load-bearing technical claims

The central diagnosis is mostly correct, but `V2.md` mixes verified facts, stale descriptions, and unproved architectural expectations.

- **Scope is correctly stated.** `V2.md`'s title, scope block, section 1 table, and section 9 all describe V2 as a rebuild of the MLIR backend and replacement of the hand emitter, not deletion of MLIR. SVM and Hybrid remain references. This matches the actual repository split: MLIR generation is isolated in `src/clifft/gpu/mlir/`, while the common HSA loader accepts an arbitrary `.hsaco` (`src/clifft/gpu/runtime/hsa_kernel_dispatch.cc:117-179`).
- **The V1 sequence-unrolling diagnosis is verified.** The three tier emitters walk `flat.instrs` on the host and append one inline IR region per instruction at `src/clifft/gpu/mlir/mlir_emit.cc:2377-2414`, `src/clifft/gpu/mlir/mlir_emit.cc:2867-2903`, and `src/clifft/gpu/mlir/mlir_emit.cc:3297-3333`. In contrast, GPU SVM executes runtime `for (pc)` loops at `src/clifft/gpu/sampler/hip_sampler.hip:728-862` and `src/clifft/gpu/sampler/hip_sampler.hip:1528-1775`. The generated MLIR comments in the oracle also contain exactly one `op[pc]` region per bytecode record: 140 for `coop_qv10.mlir`, 1,720 for `coop_circuit_d5.mlir`, 4,134 for `coop_surface_d7_t10.mlir`, and 4,296 for `glob_surface_d7_t19.mlir`.
- **The IR-size, spill, compile-time, and runtime-failure claims are substantially verified.** The oracle has `coop_qv10.mlir` at 19,936,561 bytes and its O0 LLVM IR at 13,024,044 bytes, despite only 140 instructions; the 16,432-op `surface_d11_t5` run produced 19,856,511 bytes of LLVM IR and then failed to yield a loadable code object (`results/d11err_49530.log:16-22`; `results/fullsweep_49529.log:23-33`). Global `surface_d7_t19` loaded with a 115,224-byte private segment per work-item (`results/gt19_49517.log:5-12`). The 55-224 second historical compile times are supported by `results/final_baseline_48887.log:21-37` and `results/baseline_large_48883.log:13-28`; the latter reports 192.609 seconds for `surface_d7_r7` and 224.366 seconds for `cultivation_d7`. The measured 5-60x sampling slowdown is supported by `results/perf2_49532.log:5-15` (5.1x for `frame_h`, 61.5x for `qv10`, 49.3x for `surface_d9_t10`). These are benchmark-artifact facts, not derivable from source alone.
- **“Won't link” is too imprecise.** For `surface_d11_t5`, `llc`/`lld` was reported as completing in 32.4 seconds, but the subsequent HSA loader could not open the expected `.hsaco` (`results/d11err_49530.log:19-22`). Other large cases were timeout/OOM/noncompile failures (`results/fullsweep_49529.log:23-33`). `V2.md` section 2 should say “fails to produce a usable code object reliably due to size/time/OOM,” not imply one uniform linker failure.
- **Hybrid is not a “compact-ish loop.”** `V2.md` section 1's table is wrong on this point. Hybrid also walks bytecode at code-generation time and emits a straight-line call or inline snippet per instruction (`src/clifft/gpu/codegen/emit_instructions.cc:19-224`, `src/clifft/gpu/codegen/emit_instructions.cc:231-247`; register integration at `src/clifft/gpu/codegen/emit_register_kernel.cc:75-78`, coop at `src/clifft/gpu/codegen/emit_coop_kernel.cc:148-152`, global at `src/clifft/gpu/codegen/emit_global_kernel.cc:156-170`). The oracle shows those calls directly in the generated source, for example `docs/v2/ir_reference/coop_qv10.hybrid.hip:7700-7787`. Hybrid's advantage is compiler-generated function structure and smaller per-site expansion, not a runtime bytecode loop.
- **The Hybrid oracle size is mislabeled.** `V2.md` section 2 says `coop_qv10` is 33.5k HIP lines. The actual files are 7,805 lines for `coop_qv10.hybrid.hip`, 33,508 for `coop_circuit_d5.hybrid.hip`, and 75,409 for `coop_surface_d7_t10.hybrid.hip`; `coop_surface_d7_t10.hybrid.O0.ll` is 397,938 lines. The 33.5k number belongs to `circuit_d5`, not `qv10`. The same mistake exists in the addendum's “Observation from the Hybrid IR oracle.”
- **The claim that Hybrid already supplies exact-rank/matrix body specialization is overstated.** Hybrid embeds per-circuit constant tables and emits constant axis and table indices at each call site (`src/clifft/gpu/codegen/emit_instructions.cc:76-90`, `src/clifft/gpu/codegen/emit_preamble.cc:380-399`), but the U2/U4 operand functions still receive `active_k` as a runtime value and compute runtime loop bounds (`src/clifft/gpu/codegen/ops/unitary_ops.inc:23-41`, `src/clifft/gpu/codegen/ops/unitary_ops.inc:45-80`, `src/clifft/gpu/codegen/ops/unitary_ops.inc:83-107`, `src/clifft/gpu/codegen/ops/unitary_ops.inc:110-137`). Clang may infer some values through whole-kernel optimization, but `V2.md` sections 3.1 and 3.4bis should not present that as guaranteed without ISA/IR evidence.
- **The HSA back-half is HIP-free in operation, but the stated pipeline is muddled.** The normal MLIR path is LLVM IR -> `llc` object -> `ld.lld -shared` -> HSA loader (`src/clifft/gpu/mlir/mlir_kernel_cache.cc:144-159`, `src/clifft/gpu/mlir/mlir_kernel_cache.cc:186-213`). `clang++ -x ir --offload-device-only` is only a fallback (`src/clifft/gpu/mlir/mlir_kernel_cache.cc:161-175`). More importantly, the current build compiles this code only under `CLIFFT_ENABLE_HIP` and links HIP host support (`src/clifft/CMakeLists.txt:86-124`). Thus “the back-half already contains the needed no-HIP mechanisms” is true; “the existing backend is already an end-to-end no-HIP build” is false.
- **“Keep the bytecode ISA” needs an explicit device-ABI caveat.** The VM instruction is exactly 32 bytes (`src/clifft/backend/backend.h:95-163`), but every current GPU backend actually consumes a separate flattened `GpuInstr` and flattened constant-pool layout (`src/clifft/gpu/gpu_types.h:82-116`, `src/clifft/gpu/device_program.cc:57-114`, `src/clifft/gpu/device_program.cc:301-420`). `V2.md` sections 0 and 5 currently read as if the 32-byte VM union can simply become the device ABI. It cannot without deciding whether V2 preserves `GpuInstr`, replaces it with a C-compatible packed ABI, or teaches device code the backend union layout.
- **The current “Hybrid gold” is not valid for the claimed widened qubit range.** GPU SVM and MLIR use `kPauliWords = 5` (`src/clifft/gpu/gpu_types.h:25-31`; GPU loops at `src/clifft/gpu/sampler/hip_sampler.hip:543-547`), but the current Hybrid generator still emits two-word frame storage and two-word Pauli application (`src/clifft/gpu/codegen/emit_preamble.cc:90-101`, `src/clifft/gpu/codegen/ops/frame_ops.inc:25-29`, `src/clifft/gpu/codegen/emit_coop_kernel.cc:85-97`, `src/clifft/gpu/codegen/emit_global_kernel.cc:90-99`). Hybrid remains a useful code-shape oracle, but it is not an unqualified correctness gold above 128 qubits.
- **The numeric “bit-for-bit GPU gold” claim is a requirement, not an established property.** GPU amplitudes are f32 while probability and expectation accumulation is f64 (`src/clifft/gpu/gpu_types.h:33-36`, `src/clifft/gpu/sampler/hip_sampler.hip:204-207`, `src/clifft/gpu/sampler/hip_sampler.hip:452-463`); CPU state is `std::complex<double>` (`src/clifft/svm/svm_state.cc:36-66`). However, GPU SVM disables FP contraction while Hybrid uses `-ffast-math` (`src/clifft/CMakeLists.txt:106-109`, `src/clifft/gpu/codegen/kernel_cache.cc:107-118`), and the Hybrid oracle contains `contract` floating-point operations (`docs/v2/ir_reference/coop_qv10.hybrid.O0.ll:1804-1821`). `V2.md` section 4 item 2 must freeze arithmetic flags and reduction order before exact `passed_shots` can be promised.
- **The matrix-core rejection is directionally sound, but the absolute wording exceeds the in-tree evidence.** The actual U4 body is a shared 4x4 complex matrix applied independently to many four-amplitude groups (`src/clifft/gpu/codegen/ops/unitary_ops.inc:61-79`, coop at `src/clifft/gpu/codegen/ops/unitary_ops.inc:126-136`), so packing/padding is likely unattractive. The repository does not contain a gfx950 MFMA-shape benchmark proving “trap” for all cases, so `V2.md` section 3.3 should retain the default prohibition but phrase it as a benchmark-backed policy decision, not a mathematical impossibility.
- **The “10,000 shots hide latency, therefore async is unnecessary” conclusion is unproved.** Current coop launches one workgroup per shot (`src/clifft/gpu/sampler/hip_sampler.hip:1861-1866`), while global uses a bounded set of worker workgroups that repeatedly pull shots (`src/clifft/gpu/sampler/hip_sampler.hip:1937-1979`). Actual latency hiding depends on VGPR/LDS occupancy, private-segment spills, acceptance-rate imbalance, and whether V2 launches one or multiple workgroups per CU. `V2.md` section 3.3 correctly says “measure-first,” but the preceding occupancy rationale should be stated as a hypothesis.

# 4. Validation of the 3 just-applied fixes

**(a) “Rebuild the MLIR backend, replace the emitter” — wording improved, architecture still inconsistent: PARTIAL.** The scope block, section 1 table, migration section, and section 9 consistently say that MLIR stays and `mlir_emit.cc` is replaced. There is no remaining sentence that literally recommends deleting MLIR. However, `V2.md` section 3.2 ranks plain C -> amdgcn first, section 3.2bis says Mode I may reach parity and eliminate the need for Mode S “or the dialect,” and section 6 calls the MLIR dialect optional polish. If that branch wins, the shipped path is a plain-C/HSA backend with no MLIR stage; only the old subsystem name survives. That does not satisfy the owner clarification that MLIR stays and is rebuilt. The current repository makes the distinction concrete: the MLIR stage is specifically textual MLIR -> `mlir-opt` -> `mlir-translate` (`src/clifft/gpu/mlir/mlir_codegen.cc:28-141`), after which the generic LLVM/HSA back-half begins (`src/clifft/gpu/mlir/mlir_kernel_cache.cc:144-175`). `V2.md` must specify the mandatory MLIR role even when the custom `quantum` dialect is rejected—for example, an MLIR-based interpreter IR/lowering pipeline—or explicitly obtain owner approval to redefine “MLIR backend” as “the old backend slot using only its HSA back-half.”

**(b) “Two modes on one source” — not adequate: GAP.** Section 3.2bis correctly states that an uncloned runtime operand body cannot simultaneously consume dynamic bytecode and have per-instruction constants folded. It does not resolve that tension by naming Mode I and Mode S. With `pc` dynamic, `instr.axis_1`, `instr.a`, and the selected U2/U4 matrix are dynamic loads, exactly as in the current interpreter (`src/clifft/gpu/sampler/hip_sampler.hip:728-730`, `src/clifft/gpu/sampler/hip_sampler.hip:846-850`). To make them constants while preserving a sequence loop, Mode S needs one of the following, none of which is specified:

- a `switch(pc)` or equivalent per-instruction dispatch, which recreates sequence-shaped IR;
- a table of per-instance specialized function pointers, which requires per-instance clones and likely indirect calls;
- a compact “specialization ID” micro-op stream plus a bounded set of cloned operand variants, which specializes only repeated tuples and needs explicit code-size limits; or
- weaker specialization, such as an AOT kernel family keyed only by tier/exact rank, leaving axes and matrices dynamic.

The current Hybrid code demonstrates the missing bridge: constants exist because the host emitter writes one call site per instruction (`src/clifft/gpu/codegen/emit_instructions.cc:19-90`), not because a runtime loop magically exposes bytecode values to Clang. The custom-dialect section has the same unresolved problem: a `quantum.gate_sweep` with constant attributes is naturally one IR op per gate instance; a runtime interpreter's `gate_sweep` has runtime attributes. Section 3.2bis must choose a concrete representation, define clone/cardinality and code-size budgets, and state exactly which constants remain dynamic.

**(c) “Only shots and bytecode are never unrolled” — conceptually right, document-wide fix incomplete: PARTIAL.** Section 3.1's loop taxonomy is coherent, and Mode S/section 3.4bis consistently preserve the shot and bytecode loops. But the contradiction recurs in section 0 (“keeping loops over shots, over the bytecode, and over amplitudes”) and explicitly in section 9 (“three loops—shots, bytecode, amplitudes—are never unrolled”). More importantly, “amplitude sweep may be unrolled” is dangerously broad. A U4 sweep has `2^(active_k-2)` independent groups (`src/clifft/gpu/codegen/ops/unitary_ops.inc:61-79`, coop at `src/clifft/gpu/codegen/ops/unitary_ops.inc:126-136`); fully unrolling that at global rank would reproduce catastrophic code growth. The intended rule should be: keep the group/sweep loop; specialize its bound, strides, axes, and matrix constants; permit vectorization and bounded/partial unrolling; fully unroll only the fixed 2x2/4x4 butterfly arithmetic. Sections 0, 3.1, 3.4bis, and 9 must use that exact rule.

# 5. The central bet: runtime interpreter + optional tile dialect + P2 gate

**Verdict on the central bet:** a no-HIP runtime interpreter is the right first implementation experiment because it directly bounds IR size, compile time, and live ranges, and the current GPU SVM proves the execution shape (`src/clifft/gpu/sampler/hip_sampler.hip:728-862`, `src/clifft/gpu/sampler/hip_sampler.hip:1528-1775`). It is not yet a justified final architecture. `V2.md` section 6 treats “Mode I reaches Hybrid parity” as the decision, but the existing evidence already says switch-based SVM can pay extra scalar/control cost (`PERF_ANALYSIS.md:6-22`) and that the real workload may trade steady-state throughput against per-circuit compilation. The architecture should be chosen on workload-weighted end-to-end cost, not a single parity ratio.

**The strongest underweighted alternative is a thin direct-call MLIR kernel, not full V1 unrolling.** Generate one small per-circuit MLIR function containing one direct call per bytecode instruction into a separately compiled, shared, `noinline` operand library; keep U2/U4 matrices in runtime constant-pool data; preserve immediate axes/table indices at call sites; and never inline heavy operand bodies into the kernel. This remains no-HIP and HSA-dispatched, preserves a real MLIR role, eliminates the runtime opcode switch, bounds per-operand register allocation, and produces O(sequence length) call-list IR instead of O(sequence length x operand-body size) IR. Hybrid already demonstrates the source shape: the host loop emits direct calls (`src/clifft/gpu/codegen/emit_instructions.cc:19-90`), and the generated oracle shows the call list (`docs/v2/ir_reference/coop_qv10.hybrid.hip:7700-7787`). GPU SVM's extracted heavy sweeps show why function boundaries matter (`src/clifft/gpu/sampler/hip_sampler.hip:626-680`, `src/clifft/gpu/sampler/hip_sampler.hip:1384-1464`).

This alternative conflicts with the owner's R5 requirement that the bytecode sequence remain a runtime loop, so it cannot silently replace the chosen design. It should nevertheless be an explicit adversarial benchmark control. If it is dramatically faster with acceptable compile/code size, the owner can make an informed policy choice instead of treating “sequence loop” as technically proven. The strongest requirement-compliant alternative is an **AOT exact-rank interpreter family**: precompile one runtime-loop kernel per tier/rank (or a small rank bucket set), so rank and sweep bounds specialize without any per-circuit JIT; axes and matrices stay dynamic. `V2.md` currently jumps from fully generic Mode I to an underspecified per-circuit Mode S and underweights this middle point.

**The P2 gate is not measured correctly as written.**

- **It conflates multiple variables.** Plain-C authoring, runtime opcode dispatch, persistent shot scheduling, new operand code, and HSA dispatch all change together. First compare a one-block-per-shot plain-C interpreter against GPU SVM using the same bytecode and algorithm; then add the CU-sized persistent pull loop. Current register and coop SVM scheduling is one grid item/workgroup per shot (`src/clifft/gpu/sampler/hip_sampler.hip:1778-1812`, `src/clifft/gpu/sampler/hip_sampler.hip:1861-1916`), whereas global already has persistent work pulling (`src/clifft/gpu/sampler/hip_sampler.hip:1937-2008`).
- **The circuit set is tier-biased and ambiguous.** `V2.md` section 6 says “ONE tier” and names `qv10 + circuit_d5 + surface_d7`, which are coop examples unless a suffix is specified. It misses the register tier, where dispatch dominates, and the global tier, where address spaces, HBM slots, work stealing, and scratch dominate. The repository's representative set is explicit: register `frame_h`/`circuit_d3`, coop `qv10`/`circuit_d5`/`surface_d7_t10`, and global `surface_d7_t19` (`BENCHMARKS.md:15-57`).
- **“Hybrid parity” is the wrong scalar decision rule.** Report at least: cold device compile time; `.hsaco` load/bind time; warm kernel time; whole-call wall time; code-object/IR size; VGPR/SGPR/private/group segment; and throughput over a matrix of shots per circuit and number of distinct circuits. The pre-V2 analysis identified circuit variety versus shots per circuit as decisive, but `V2.md`'s P2 gate drops that workload dimension.
- **Use a factorial baseline set.** Measure GPU SVM, plain-C Mode I with one-block-per-shot scheduling, plain-C Mode I with persistent scheduling, exact-rank AOT Mode I, Hybrid, and the thin direct-call MLIR control. Dispatch every loadable `.hsaco` through the same HSA path where possible; otherwise host-runtime differences contaminate the result. Current Hybrid and MLIR already share `PersistentDispatcher` in the host path (`src/clifft/gpu/sampler/hip_sampler.hip:2267-2346`, `src/clifft/gpu/sampler/hip_sampler.hip:2347-2429`).
- **Define pass/fail thresholds before running.** A generic interpreter 20-30% slower in warm kernel time may still be the correct product if it removes seconds or minutes of compile time across many distinct circuits. Conversely, warm parity on 10,000 shots does not justify the design if one-shot/low-shot RL latency or register-tier dispatch is poor. The gate needs an explicit weighted objective based on observed RL rollout distributions.
- **P2 cannot decide custom-dialect ROI without any dialect comparator.** It can decide whether generic Mode I is sufficient. If not, a separate P2b must implement one narrow specialization both as plain-C/LLVM and as a minimal MLIR lowering—fixed-rank U2/U4 plus a distribution-derived measurement reduction—before authorizing a full dialect. `V2.md` sections 3.4bis and 6 currently claim both “measure the specialization both ways” and “do not build the dialect before this measurement,” which is circular unless the minimal comparator is defined.

The optional tile dialect should be treated as a targeted solution to layout/reduction/specialization problems, not as the default answer to interpreter overhead. The highest-value first tile abstraction is the lane-to-amplitude distribution and convergent reduction, not a general async pipeline; current cooperative measurement is explicitly a reduction/barrier problem (`src/clifft/gpu/sampler/hip_sampler.hip:1213-1325`), while the 2x2/4x4 gate bodies are already simple strided loops (`src/clifft/gpu/codegen/ops/unitary_ops.inc:23-80`).

# 6. Underweighted risks

**Switch dispatch: “divergence” is mostly the wrong concern; branch and instruction-cache cost are real.** In both interpreter loops, all cooperating lanes read the same `program.instrs[pc]` (`src/clifft/gpu/sampler/hip_sampler.hip:728-731`, `src/clifft/gpu/sampler/hip_sampler.hip:1528-1531`). Register-tier lanes represent different shots, but they still execute the same circuit and same `pc`; discarded lanes become inactive rather than selecting different opcodes. Therefore the top-level switch does not inherently diverge a wave. The risks are a hot 40-way control transfer, extra scalar instruction/address work, inhibited scheduling across operand boundaries, and a code object containing all opcode bodies. `PERF_ANALYSIS.md:6-22` reports +35% SALU in one interpreter comparison, though that experiment was also confounded by VGPR pressure from inlined extended handlers. `V2.md` section 8 question 2 should say “dispatch/control-flow and i-cache pressure,” reserve “divergence” for data-dependent branches inside operands, and prohibit heterogeneous circuits sharing one wave if shot packing or device queues are later generalized.

**The plain-C -> amdgcn toolchain is not ready on this installation.** I ran capability checks on the review host:

- `/usr/bin/clang` and `clang++` are Ubuntu Clang 14.0.0. They register `amdgcn` but reject `-mcpu=gfx950`. `llc` and `ld.lld` are not on `PATH`.
- `/shared/jmonsalv/software/modules/llvm/upstream_05082025/bin/{clang,llc,ld.lld,mlir-opt,mlir-translate}` exist and report LLVM/Clang/MLIR 21.0.0git at commit `20d6375796073f6a0f0ea6abe05ce454a3d617ff`. `llc` registers AMDGPU and lists `gfx950`; Clang accepts an `amdgcn-amd-amdhsa`/`gfx950` dry run.
- That Clang dry run fails with “cannot find ROCm device library” unless `-nogpulib` is supplied. The shared LLVM tree has no `ocml.bc`, `ockl.bc`, or gfx950 OCLC bitcode in its resource directory.
- Existing CMake caches refer to `/opt/rocm-7.2.3/lib/llvm/bin/clang++` and ROCm 7.2.3 device libraries, but `/opt/rocm-7.2.3` and `/opt/rocm` are absent on the review host. No ROCm module is available, and the normal system HSA headers/library are absent here.

The conclusion is narrower than “plain C is impossible”: a bare kernel using Clang AMDGPU builtins and no device library is realistically compilable with the shared LLVM 21 toolchain, and the existing `llc`/`ld.lld`/HSA path proves the back-half on compute nodes (`src/clifft/gpu/mlir/mlir_kernel_cache.cc:144-175`, load at `src/clifft/gpu/runtime/hsa_kernel_dispatch.cc:117-179`). But a full interpreter uses operations such as device `log` in noise sampling (`src/clifft/gpu/sampler/hip_sampler.hip:253-275`) and requires a stable kernel annotation/ABI, barriers, atomics, and code-object metadata. `V2.md` section 3.2's “lowest infra; try first” is an assumption until a checked-in toolchain probe produces a gfx950 `.hsaco`, loads it via HSA, executes it, and covers a math/device-library function or a declared replacement. The design must pin exact LLVM/MLIR/ROCm versions and paths; relying on `PATH`, `/opt/rocm`, and stale cache configuration is not acceptable.

**The current build graph violates the intended product boundary.** HSA runtime, HSA loader, and MLIR sources are all compiled only inside `if(CLIFFT_ENABLE_HIP)`, after `enable_language(HIP)`, and `clifft_core` links `hip::host` (`src/clifft/CMakeLists.txt:86-124`). The runner is also HIP-gated (`CMakeLists.txt:187-194`). V2 needs separate options such as `CLIFFT_ENABLE_HSA`, `CLIFFT_ENABLE_HIP_REFERENCE`, and `CLIFFT_ENABLE_MLIR_V2`; otherwise “NO HIP” cannot be validated by configuration or CI. A no-HIP CI job must fail if HIP libraries, `-x hip`, HIP headers, or HIP runtime symbols enter the shipped target.

**A custom dialect is a qualitatively new compiler product, not a modest extension of the current MLIR path.** Today the repository emits textual built-in LLVM dialect and invokes external tools; it deliberately has no MLIR C++ library linkage (`src/clifft/CMakeLists.txt:115-124`, `src/clifft/gpu/mlir/mlir_codegen.cc:28-141`). A real `quantum` dialect requires TableGen definitions, custom types/attributes, parsers/printers/verifiers, conversion legality, type conversion, multiple lowering passes, pass registration, CMake linkage to version-pinned MLIR libraries, canonicalization tests, diagnostics, serialization/version policy, and ongoing adaptation to MLIR API churn. `V2.md` sections 3.2 and 3.3 acknowledge “most infra” but do not estimate ownership, build/package impact, or a deletion criterion. The document should require a minimal dialect RFC and maintenance budget before P2b, not authorize “progressive lowering” as an amorphous fallback whenever Mode I misses parity.

**“Unify the three tiers” understates address-space and execution-model differences.** The current MLIR emitter selects `!llvm.ptr<3>` specifically for LDS amplitude loads/stores and generic pointers for other tiers (`src/clifft/gpu/mlir/mlir_emit.cc:210-230`); coop defines address-space-3 globals and workgroup state (`src/clifft/gpu/mlir/mlir_emit.cc:2638-2659`), while global uses generic HBM pointers, per-slot offsets, half-sized scratch, and XCD work stealing (`src/clifft/gpu/mlir/mlir_emit.cc:2996-3023`, `src/clifft/gpu/mlir/mlir_emit.cc:3042-3074`). In plain C, erasing those distinctions behind one generic pointer can introduce `addrspacecast`s, lose alias/address-space information, or be illegal for LDS operations. “One source” is realistic only if lowering produces separate typed functions/kernels per storage model. It does not imply one binary ABI or one function body. The design must define a common semantic interface plus tier-specific storage/cooperation adapters and prove the generated IR retains address spaces.

**The f32/f64 model is underspecified and may defeat both correctness and single-source claims.** CPU stores complex f64 (`src/clifft/svm/svm_state.cc:36-66`); GPU stores complex f32, performs basic complex multiply in f32, scales through f64 then truncates, and accumulates norms in f64 (`src/clifft/gpu/sampler/hip_sampler.hip:186-207`). Branch sampling is sensitive to those sums (`src/clifft/gpu/sampler/hip_sampler.hip:242-250`), as is the CPU reference (`src/clifft/svm/svm_internal.h:62-79`). V2 must freeze:

- storage precision for amplitudes, fused matrices, gamma, probability sums, reductions, and expectation values;
- contraction/FMA policy, denormal mode, fast-math flags, reassociation, and reduction tree;
- the exact log/noise-hazard implementation and RNG-consumption order;
- whether Mode I and Mode S must be bit-identical to each other, not merely statistically equivalent;
- a statistical acceptance model against CPU f64 and an exact per-shot/record model against the GPU f32 reference where arithmetic semantics are identical.

Without this, “one source” can still generate numerically different backends, and constant folding in Mode S can change rounding relative to Mode I.

**The device ABI is not frozen.** The 32-byte VM `Instruction` is not the current GPU wire format; `flatten_program` expands it into `GpuInstr` plus several device-specific arrays (`src/clifft/gpu/device_program.cc:57-114`, `src/clifft/gpu/device_program.cc:301-420`). There is no `static_assert` for `GpuInstr` size/offsets, no C-compatible shared ABI header, and no version field. Plain C, MLIR, host C++, cache keys, and oracle generation all need one audited layout with offset assertions on the host and LLVM-side tests. Otherwise V2 will repeat the struct-layout failures it cites.

**Forced-measurement support has no GPU gold today.** `V2.md` section 8 says `OP_*_FORCED` must flow through the interpreter unchanged, but current GPU validation excludes those opcodes (`src/clifft/gpu/device_program.cc:13-54`) and the GPU test explicitly expects rejection (`tests/test_gpu_sampler.cc:142-151`). CPU is the only implementation. V2 must either put forced execution in scope with a new device ABI and CPU differential tests, or remove the claim that GPU SVM is gold for every opcode.

**Persistent scheduling and memory sizing are not solved by “one workgroup per CU.”** Current global scheduling uses approximately two workgroups per CU (`src/clifft/gpu/sampler/hip_sampler.hip:2057-2071`) and allocates one full statevector plus half-state scratch per worker (`src/clifft/gpu/sampler/hip_sampler.hip:2159-2170`). At higher rank, the number of resident slots must be chosen from available HBM, desired occupancy, and shots—not fixed at 512. Tail behavior also changes with postselection and circuit depth. The scheduler needs a formula and measured policy, not the IRIS slogan.

**Host concurrency and cache invalidation are omitted.** The HSA loader documents a single-host-producer constraint for each loaded kernel (`src/clifft/gpu/runtime/hsa_kernel_dispatch.h:16-47`), and `PersistentDispatcher` is explicitly not thread-safe (`src/clifft/gpu/runtime/hsa_persistent_dispatch.h:51-53`). RL callers may submit circuits concurrently. Mode I/Mode S must define queue ownership, kernarg/signal pools, and synchronization. Mode S cache keys must include source/ABI version, target features, compiler versions, lowering pipeline, optimization flags, numeric mode, and specialization schema; the current MLIR cache hashes only LLVM IR plus arch (`src/clifft/gpu/mlir/mlir_kernel_cache.cc:186-205`).

# 7. Concrete recommended FIRST SLICE

Implement a **fixed-rank-10 coop interpreter for the qv10 opcode subset**, compiled from plain C with no device libraries, loaded and dispatched through HSA. Put two entry points in the same device source: one block per shot and a persistent atomic-pull version. Do not extract all operands, implement global/register tiers, build Mode S, or create a dialect.

This is the smallest useful slice because `qv10` is only 140 bytecode instructions but exercises frame updates, runtime dispatch, rank growth, U2/U4 constant-pool reads, cooperative amplitude sweeps, measurements, barriers, and RNG. Its actual opcode set in the oracle is only `OP_FRAME_H`, `OP_FRAME_S`, `OP_ARRAY_ROT`, `OP_ARRAY_U2`, `OP_ARRAY_U4`, `OP_EXPAND_ROT`, `OP_MEAS_ACTIVE_INTERFERE`, and `OP_SWAP_MEAS_INTERFERE` (`docs/v2/ir_reference/coop_qv10.mlir`, 140 `op[pc]` records; opcode definitions at `src/clifft/backend/backend.h:25-85`). Add only `OP_OBSERVABLE` for the differential-test fixture. That is enough to test the core interpreter and toolchain bet without the noise-path device-library problem.

It must compare direct versus persistent scheduling before attributing any difference to interpretation.

**Predeclared prove/kill criteria:**

- **Kill the plain-C front-end** if the no-HIP toolchain cannot reproducibly produce and HSA-load a gfx950 code object from a clean build, or if the executable links any HIP runtime component.
- **Kill the proposed ABI** if host/device offset tests fail or the same `.hsaco` cannot consume `flatten_program` output without an extra re-encoding pass.
- **Kill the operand implementation** on any exact mismatch versus GPU SVM for the observable fixture at any tested seed. Do not average correctness.
- **Kill the plain-C implementation quality** if direct scheduling is more than 1.35x slower than GPU SVM kernel time on qv10 after matching scheduling/algorithm and excluding host dispatch. That result would mean the authoring/lowering path itself is losing badly.
- **Do not kill the interpreter architecture merely for missing Hybrid parity.** If it is close to GPU SVM but 20-35% behind Hybrid, proceed to the workload-amortization gate and exact-rank AOT experiment. Only then decide whether specialization is economically required.
- **Proceed to more opcodes/tiers only if** IR and code-object size are circuit-independent, private spill is negligible, correctness is exact, and the persistent variant is measured rather than assumed to help.

This slice proves the no-HIP compiler/loader path, the real device ABI, the hot switch, cooperative barriers/reduction, and scheduler choice. It intentionally does not “prove” a dialect, all-tier unification, or Mode S.
